## 1) Audit conclusion

The correct version-boundary judgment is:

1. `1.6.x` must absorb already-discovered current-universe protocol debt to closure instead of exporting it into `1.7.x` under a new label.
2. `1.7.x` should begin only where the dominant work is genuinely future-facing:
   - new object classes,
   - new relation/topology classes,
   - new machine capability classes.
3. Any topic whose true remedy still lies inside existing `1.6.x` owner lanes, shared creator/backfill/producer/consumer infrastructure, or runtime replay closure remains `1.6.x` work.

## 3) Frozen audit boundary

### 3.1 A topic remains `1.6.x` when

1. the semantic owner already exists inside the `1.6.x` universe;
2. the missing part is machineization, shared infra wiring, or runtime replay closure;
3. the topic can be closed without inventing a new protocol ontology.

### 3.2 A topic may start `1.7.x` when

1. the dominant question is no longer “how do we finish closing the current universe?”;
2. the dominant question becomes “what new object / relation / capability should the next universe contain?”;
3. the work would otherwise distort `1.6.x` if forced into the current ontology.

## 4) Practical audit rule for future triage

When a new topic appears, audit must classify it in this order:

1. Is this unresolved `1.6.x` closure debt inside the current protocol universe?
2. If yes, it stays in `1.6.x`.
3. If no, does it require a new object, relation, or capability class beyond the current universe?
4. If yes, it is a valid `1.7.x` candidate.

## 5) Final audit sentence

`1.6.x` should be closed as the line that makes the current identity-protocol universe root-closed, machine-closed, and runtime-closed. `1.7.x` should start only after that boundary is respected, and only for genuinely future-facing protocol expansion.
